**Refined Paragraph:** **Pre-Execution Defenses.** Pre-execution defenses emphasize the systematic examination of agent components to ensure compliance with safety and security standards. For instance, tools such as MCP-watch [19] are employed to audit the source code of tools interfacing with the agent. Moreover, frameworks like MCP-scan [20] are concurrently utilized to conduct comprehensive scans of MCP servers, with the goal of identifying security vulnerabilities, including prompt injection risks, tool poisoning, and toxic execution flows. These static analyses play a critical role in fortifying the agent against threats prior to deployment. **Runtime Defenses.** During the operational phase, dynamic defenses are indispensable for the immediate mitigation of emerging threats. Several methodologies have been proposed to address these challenges. Notably, SLM as Guardian [46] leverages a small model to detect and flag potentially harmful user queries. Furthermore, the structured queries approach [47] has been developed to prevent prompt injection by enforcing a strict separation between developer prompts and user data, thereby reducing the risk of manipulation attacks that exploit this conflation. These strategies collectively enhance the system’s robustness against runtime security threats. **Post-Execution Defenses.** In the post-execution phase, analyses are conducted to evaluate the agent’s actions and identify potential discrepancies. These evaluations typically rely on procedural records of the agent’s operations. While the LLM-as-a-Judge paradigm offers a cost-effective alternative to human inspection [48], its efficacy is contingent upon known risk patterns [49], rendering it less effective when addressing novel security challenges. Consequently, its applicability to emerging agent security scenarios remains limited. **LLM-Agent Architecture.** We consider a contemporary LLM-agent configuration that adheres to the Model Context Protocol (MCP). In this architecture, the LLM functions as the central reasoning entity, tasked with autonomously interpreting user directives, delineating intermediate reasoning steps, and invoking external tools to fulfill sub-tasks. Each MCP tool operates as an independent module within the agent and communicates with the LLM through a standardized API interface. Furthermore, during task execution, the LLM maintains contextual awareness across tool calls, which facilitates complex, multi-step reasoning processes. This design underscores the modularity of the MCP tools, which act as executors of specialized functions while the LLM serves as the cognitive core of the system. **Adversary Model.** The adversary’s primary objective is to exploit the computational resources of the victim agent without obtaining elevated privileges or compromising the integrity of the host system. However, the adversary cannot access the agent’s internal state, memory, or governing parameters. Moreover, they are unable to modify the platform’s sandbox environment or runtime policies.
