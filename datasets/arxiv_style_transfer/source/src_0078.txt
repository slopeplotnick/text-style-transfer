Faulty code isn’t running. For our method to work, bad lines of code need to run in at least one test that fails. If a line never runs, we can’t figure out what’s wrong with it. So, if the tests don’t cover enough of the code, we might miss some problems. We try to deal with this by using several failing tests and some quick static analysis. About bounded model checking (BMC): we use limited versions of programs. Things like loops and depth limits can leave out possible behaviors, which means some valid problems might not show up because of the limits we set. Also, when we cut off iterations, problems that show up in the limited version might not apply to the full program. We set these limits carefully and share them with the results, but the limits are a built-in drawback. For pointers, arrays, and undefined behavior: like we said in Section 5.1, CFAULTS uses tools like CPPCHECK and CLANG-TIDY to find things like uninitialized variables and runtime errors, like dividing by zero. If it finds any of these problems, CFAULTS stops and tells the user. It also uses CBMC’s memory-safety checks to catch bad memory actions, like going out of bounds or doing unsafe pointer math. But CFAULTS follows CBMC’s rules for ANSI C, so anything CBMC says is fine gets treated as fine by us too, and anything CBMC doesn’t flag might get missed. Making CBMC’s setup match the intended C rules better is something we’ll work on later. For external validity: we tested this on benchmark and student programs that compile correctly and have clear specs, like assertions or expected outputs. Applying this to bigger programs, ones with lots of input/output, concurrency, or complicated libraries, or to specs written in more advanced ways, might need more work and could change the results we got here.
