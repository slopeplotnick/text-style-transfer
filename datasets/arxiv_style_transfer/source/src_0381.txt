We made our method work well with modern systems that handle a lot of data quickly, like vLLM and SGLang, and it can be used for both live services and offline processing. In Section 4.2, we mostly use the two-step vLLM setup because it’s fast and makes it easy to deal with reasoning steps. We tested THINKMERGE in two ways. First, for tasks where there’s only one right answer, we looked at AIME 2025 and GPQA Diamond, where you can combine multiple answers using majority voting. Second, for tasks where there’s no single correct answer, we tested on LiveCodeBench v5, BrowseComp-en, BrowseComp-zh, GAIA, and xBench-DeepSearch, where the focus is on creating one good solution. For tasks with one right answer, we did five tests and checked models like Qwen3-4B, Qwen3-14B, and DeepSeek-R1-Distill-Qwen-7B. For coding tasks with open-ended answers, we used models like DeepCoder-14B-Preview, Qwen3-8B, Qwen3-Coder-30A3B-Instruct, Qwen3-4B-Thinking, and Qwen3-Think-30A3B. For open-ended research tasks, we used WebSailor models like WebSailor-3B, WebSailor-7B, and WebSailor-32B. We set the maximum sequence length to 32,768 tokens, and details about sampling settings are in Appendix A.1. We also checked if THINKMERGE works for research tasks where the model has to think and use tools before giving an answer. Specifically, we tested three Tongyi-WebSailor models—WebSailor-3B, WebSailor-7B, and WebSailor-32B—on four tough web-based tests: BrowseComp-en, BrowseComp-zh, GAIA, and XbenchDeepSearch. BrowseComp-en and BrowseComp-zh focus on hard-to-find factual questions in English and Chinese. Since BrowseComp-en has a lot of questions (1,266 total), we picked 200 randomly to test, so it’s about the same size as BrowseComp.
