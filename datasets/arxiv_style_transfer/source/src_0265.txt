GraphMatch works well with cold start nodes, similar to TextMatch. This shows the model can use text embeddings when there's no graph info, helping with the cold start issue. GraphMatch's setup has three parts: a feature store, an inference service, and a graph database. These parts let different GNN models use specific node features while sharing one graph structure for different needs. Node sampling is done with Cypher, where users pick the node and edge types they need for inference. The feature store mainly has stats like counts and averages. We use Snowflake to keep copies of production databases and business data. Feature tables are updated hourly using SQL Mesh jobs and stored in Feast. If features are missing for nodes in the graph but not yet in the feature store, we use default values. The graph database uses Neo4j Aura. Two pipelines update it: a Kafka pipeline for fast-changing entities like job posts and an hourly Airflow pipeline for other entities. The database keeps basic node info like type, ID, and timestamp to help with subgraph sampling for inference. The inference service runs the model on a Python/FASTAPI microservice, deployed on EC2 instances with Nvidia A10G GPUs. Autoscaling is based on requests per second since GPU/CPU usage isn't as reliable for predicting latency issues. To make inference faster, we cache TextMatch embeddings whenever a freelancer profile or job post description is updated, so online inference only uses the GNN layers. This keeps embedding generation times under 70 milliseconds per embedding for all entity types, allowing scalability and supporting real-time use cases.
