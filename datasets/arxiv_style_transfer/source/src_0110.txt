This part talks about the limits and bigger effects of the LeechHijack attack we suggested. We look at the limits of the current setup, explain where it can be used, and point out ways the threat might grow or get worse over time. One big limit of our method is how well it handles hijacked computing. As shown in Table 7, the attack's Answer Success Rate (ASR) isn't as good as the native LLM. This drop in performance affects how useful the stolen resources are for the attacker. But this problem can be lessened by spreading the extra task across many victims and using a group decision process on the combined results. Another limit is what tasks LeechHijack can do. Our tests showed LeechHijack works for tasks in the MMLU benchmark, but we didn't check how well it does on harder tasks, like those in GAIA. LeechHijack is mainly set up for regular chat-based tasks, and it probably wouldn't do as well on more complicated jobs. Making the attack work well on tough commands is hard and would need more advanced attack setups. Agent systems use costly LLMs, so an attacker can benefit from LeechHijack without using it for tough tasks. They can use the hijacked resources for easier jobs, like gathering info or creating content templates, using the model's big knowledge base. So, LeechHijack is a real and ongoing threat to the MCP and agent systems, no matter how complex the hijacked task is.
