We don't know anything beforehand about the stuff we're measuring, other than that the measurements are continuous and have a limited average and spread. So, we treat energy use like a normal distribution because it doesn't bring in extra assumptions and makes things easier to handle without complicated math, which speeds up our analysis. We also use a multi-level model with a non-centered setup to make our model work better and faster without messing up the results. We do this in Java 21, but it can work with any statically typed language that runs on the JVM. We're focusing on a part of Java to see if our method works. All the Java code is turned into Java bytecode by the OpenJDK 21.0.6 compiler. To cut down on outside interference and make sure the energy measurements are the worst-case energy consumption, we control several things that can affect energy use: we turn off dynamic class unloading and JIT compilation in the Java runtime system and run it in interpreted-only mode. We also set the CPU speed to its lowest at 1.5GHz and turn off wireless networking on the platform. The benchmark setup has 174 small tests. Each test is set up by operation, data type, and data size. For data types, we look at 32- and 64-bit integers and floating-point types, plus reference types for arrays and objects. For example, we have three patterns for adding int, long, double, and float (one for each data size), making 12 addition patterns in total. Arrays and objects are different from operations on basic data types. We model one array for each basic data type of size one. For objects, we model them from classes and static nested classes, each having four fields, one for each basic data type.
