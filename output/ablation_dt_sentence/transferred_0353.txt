A Software Product Line (SPL) is a systematic approach to deriving a set of related software systems from an existing code base that shares common features, with the goal of enabling the rapid and flexible creation of new software products. This extractive process, which involves migrating an existing code base into an SPL, is inherently complex and time-consuming. Moreover, it can significantly impact well-established development workflows and practices within the organization managing the code base. This paper presents the preliminary steps taken to initiate this migration process, which we consider to be long overdue, and positions this work as a foundation for subsequent efforts in this direction. The study was conducted in collaboration with ITK – Predict and Decide, a small and medium-sized enterprise (SME) that chose to migrate its code base into an SPL. As researchers, our role was to support and guide the company throughout this transition. The ITK code base is structured around a central platform known as Cross, which constitutes a comprehensive framework where software reuse is already a well-established practice. While this framework shares similarities with a Software Product Line (SPL), it lacks the formal models and structured processes typically associated with a conventional SPL. To assist the company’s developers, we planned a gradual transition that would involve reorganizing both the code base and the engineering practices. Our first task was to assess the perceptions of the company’s personnel regarding the proposed change and provide recommendations to help facilitate the adaptation process. This paper outlines the findings from this initial study. We conducted interviews with key stakeholders to gather insights on their current operational practices, their expectations for the SPL migration, and the concerns they had about the transition. Overall, the majority of participants expressed a favorable attitude toward the adoption of an SPL approach and demonstrated a strong willingness to actively participate in the process. Developers, in particular, viewed the migration as an opportunity that combined both technical and managerial challenges, showing great enthusiasm for engaging with the associated tasks. In contrast, stakeholders more closely involved in business activities voiced greater reservations, highlighting potential risks such as increased maintenance complexity and possible constraints on creativity, especially in UI/UX design.
