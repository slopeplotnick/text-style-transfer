GraphMatch demonstrates performance on cold start nodes that is comparable to that of TextMatch, suggesting its capacity to effectively rely on text representations when graph-based signals are absent. This ability to fallback to text embeddings mitigates the cold start challenge. The architecture of GraphMatch consists of three primary components: a feature store, an inference service, and a graph database. This modular design allows for a shared graph structure while enabling distinct GNN models to leverage customized node features, catering to diverse applications. Node sampling is performed using Cypher [7], which enables users to specify the required node and edge types for inference. The feature store predominantly includes statistical aggregates, such as counts and averages, reflecting a design choice that prioritizes richer feature sets over minimal representations. Our data warehouse, Snowflake [30], stores copies of production databases alongside various business data. Feature tables are generated through hourly SQL Mesh ETL jobs and persistently managed within Feast. In cases where node features are missing in the graph but not yet incorporated into the feature store, default values are used to maintain consistency and facilitate inference. The graph is hosted on the Neo4j Aura graph database [24]. Two ETL pipelines update the graph: a near real-time Kafka pipeline for rapidly evolving entities, like job posts, and an hourly Airflow batch pipeline for other entities. The graph database maintains minimal node properties, including type, unique identifier, and creation timestamp, to facilitate accurate subgraph sampling during inference. The inference service operates the model via a Python/FASTAPI microservice, hosted on EC2 instances equipped with Nvidia A10G GPUs. Autoscaling is driven by the rate of incoming requests per second, as GPU/CPU resource utilization is less reliable in predicting potential latency degradation. To optimize inference speed, TextMatch embeddings are computed and cached whenever a freelancer profile or job post description is updated, restricting online inference to the GNN layers alone. This approach keeps average embedding generation latencies below 70 milliseconds per embedding across all entity types, thus supporting horizontal scalability and enabling near real-time applications.
