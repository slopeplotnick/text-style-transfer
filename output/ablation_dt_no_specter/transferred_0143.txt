Pre-Execution Defenses. Pre-execution defenses emphasize the static analysis of agent components to ensure operational security and integrity. For instance, tools such as MCP-watch [19] are specifically designed to audit the source code of tools integrated with an agent. Concurrently, frameworks like MCP-scan [20] systematically analyze MCP servers to detect a range of security vulnerabilities, including those susceptible to prompt injection, tool poisoning, and other forms of exploitation. Runtime Defenses. During the agent's execution, dynamic defenses are crucial for real-time threat mitigation. Several methodologies have been proposed to address this challenge. For example, SLM as Guardian [46] employs a lightweight model to identify and flag potentially harmful user queries. Moreover, to prevent prompt injection, a method enforcing a strict separation between developer prompts and user data has been implemented, thereby fortifying the system against manipulation attacks. Post-Execution Defenses. Post-execution analyses are conducted to examine procedural records of agent operations and identify potential issues. While the LLM-as-a-Judge approach offers a cost-effective alternative to human evaluation, it remains dependent on known risk patterns and does not adequately address emerging security challenges. We examine a contemporary LLM-agent architecture that employs the Model Context Protocol (MCP). Within this framework, the LLM functions as a coordinator, tasked with interpreting user directives, formulating intermediate reasoning steps, and utilizing external tools to accomplish sub-tasks. Each MCP tool operates autonomously within the agent, interfacing with the LLM via a standardized API. During task execution, the LLM maintains contextual memory that persists across tool calls to facilitate intricate reasoning. Thus, the LLM serves as the principal cognitive entity, while the tools perform designated tasks. The adversary's goal is to exploit the agent's computational capabilities without obtaining elevated privileges or compromising the host system. We conceptualize the adversary as a third-party MCP tool provider who can publish and distribute tools within the open market. This entity cannot directly access the agent's internal state, memory, or parameters, nor can it alter the platform's sandbox or runtime policy. All interactions occur through legitimate MCP calls.
