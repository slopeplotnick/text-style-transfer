Pre-Execution Defenses. Before initiating execution, we prioritize a comprehensive assessment of agent components to ensure their security. For instance, tools like MCP-watch rigorously audit the source code associated with the agent's integrated functionalities. Concurrently, frameworks such as MCP-scan perform systematic examinations of MCP servers to detect vulnerabilities, including those susceptible to prompt injection or other interference forms. Runtime Defenses. During the operational phase, implementing dynamic mechanisms for real-time threat mitigation is crucial. Several methodologies have been proposed. The concept of SLM as Guardian, for example, employs a compact model to identify potentially malicious user queries. Moreover, a method specifically aimed at mitigating prompt injection has been introduced, enforcing the segregation of developer prompts from user data and thereby strengthening the system against manipulation attempts. Post-Execution Defenses. Typically, post-execution assessments employ procedural documentation of agent activities to identify potential issues. Although the LLM-as-a-Judge mechanism offers a cost-effective alternative to human evaluation, its efficacy is mainly limited to pre-existing security threats and remains inadequate for addressing emergent vulnerabilities. We consider a contemporary LLM-agent configuration utilizing the Model Context Protocol (MCP). Within this framework, the LLM acts as a coordinator, interpreting user directives, devising intermediate reasoning processes, and deploying external tools to accomplish specific sub-tasks. Each MCP tool operates autonomously within the agent, engaging with the LLM through a standardized API interface. During task execution, the LLM retains an awareness of operational dynamics, facilitating sophisticated reasoning between tools. It serves as the cognitive nucleus by delegating distinct functionalities to specialized tools. However, adversaries aim to exploit the agent’s computational resources without unauthorized access or system infiltration. We model the adversary as a third-party MCP tool provider distributing tools within the open ecosystem. This entity lacks direct access to the agent’s internal state, memory, or parameters and cannot modify the platform's sandbox or runtime policy.
