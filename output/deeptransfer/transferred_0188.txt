We have no prior knowledge about the factors being measured, except that the observations are continuous and have finite mean and variance. Therefore, we model energy consumption as a Gaussian distribution (see Eq. 1), as this choice avoids introducing additional assumptions and offers a mathematically convenient framework that simplifies further analysis and accelerates computations compared to alternative distributions. Furthermore, we employ a hierarchical model (Section 2) with a non-centered parameterization, which optimizes computational efficiency and enhances model convergence without compromising the validity of the results. Our methodology is implemented in Java 21, although it is applicable to any statically typed programming language running on the JVM. To evaluate the effectiveness of our approach, we focus on a specific subset of Java (see Tab. 1). The Java source code is compiled into Java bytecode using the OpenJDK 21.0.6 compiler. To minimize external interference and ensure the energy measurements reflect the worst-case energy consumption (WCEC), we apply several control measures to reduce variability in energy usage. Specifically, for the Java runtime system, we disable dynamic class unloading and JIT compilation, operating exclusively in interpreted-only mode. For the experimental platform, we fix the CPU frequency to its lowest setting, 1.5 GHz, and deactivate wireless networking hardware. The benchmarking framework consists of 174 microbenchmarks, each parameterized by operation, data type, and data size. The data types profiled include 32-bit and 64-bit integers (int and long), floating-point types (float and double), and reference types for arrays and objects. Table 2 summarizes the data sizes, while Table 1 details all operations, where each operation may exhibit varying Bytecode patterns. For example, we model three distinct Bytecode patterns for addition operations on int, long, double, and float data types, corresponding to each data size, resulting in a total of 12 addition operation patterns. Operations involving arrays and objects differ from those on primitive data types. Specifically, we model one array per primitive data type, each of size one. For objects, we construct models based on classes and static nested classes, each containing four fields corresponding to the fundamental primitive data types.
