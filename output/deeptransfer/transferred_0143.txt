Pre-Execution Defenses. Pre-execution defenses emphasize the static analysis of agent components. For example, tools such as MCP-watch are utilized to audit the source code of components integrated with the agent. Simultaneously, frameworks like MCP-scan systematically analyze MCP servers to detect a variety of security vulnerabilities, including those prone to manipulation or exploitation. Runtime Defenses. During the agent's execution, dynamic defenses are crucial for real-time threat mitigation. Several methodologies have been proposed to address this challenge. For instance, the SLM-as-Guardian framework employs a lightweight model to identify and intercept potentially malicious user queries. Moreover, to mitigate prompt injection vulnerabilities, a structured queries approach has been developed that enforces a strict separation between developer prompts and user data, thereby enhancing the system's resilience against manipulation. Post-Execution Defenses. Post-execution analyses rely on procedural records of agent operations to identify potential issues. Although the LLM-as-a-Judge approach offers a cost-effective alternative to manual evaluations, it is limited to known risks and may not adequately address emerging security challenges. We examine a contemporary LLM-agent architecture employing the Model Context Protocol (MCP). Within this framework, the LLM functions as a coordinator, tasked with interpreting user instructions, devising intermediate reasoning steps, and orchestrating the invocation of external tools to accomplish specific sub-tasks. Each MCP tool operates autonomously within the agent, interfacing with the LLM through a standardized API to ensure seamless communication and integration. During task execution, the LLM maintains a persistent contextual awareness, even when transitioning between tools, to facilitate complex reasoning processes. Thus, the LLM serves as the central reasoning entity, while the tools execute specialized tasks. The adversary's goal is to exploit the agent's computational capabilities without necessitating additional access or breaching the system's security protocols. We conceptualize the adversary as a third-party MCP tool provider who disseminates tools within the open ecosystem. However, the adversary lacks the capability to access the internal state of the agent or modify the system's policies. Their interaction is confined to legitimate MCP invocations.
